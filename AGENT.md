# AGENT.md

Guidance for AI coding agents (and people) working in this repository.

## What this repository is

`stripe-apiroute` publishes a Python client for the Stripe API. The client is **generated** by [apiroute](https://github.com/dougyouch/apiroute) from Stripe's published OpenAPI spec (the SDK variant, `spec3.sdk.json`). Methods are named from the spec's `x-stripeOperations`, the names Stripe's own SDKs use. The client is kept current by the weekly Build workflow, and released to PyPI as `stripe-apiroute`.

## Layout

| Path | What it is | Edit by hand? |
| --- | --- | --- |
| `apis.yaml` | The API: spec URL, docs URL, module, client class, auth base class, the operation-name map | **yes**: this is the source of truth |
| `specs/stripe.json` | The committed copy of the spec, written by `scripts/generate.py --fetch` | no (fetch it) |
| `specs/stripe.names.json` | Operation ID → Stripe's dotted name, written by `generate.py` from the spec | no (regenerate) |
| `scripts/generate.py` | Fetches the spec, writes the name map and `spec_info.py`, runs `apiroute generate`, writes the README table | yes |
| `scripts/stripe_names.py` | How Stripe's names become sections and methods (see its docstring) | yes |
| `scripts/next_release.py` | Each release's version, notes and CHANGELOG.md entry, from the commits since the last tag | yes |
| `src/stripe_apiroute/auth.py` | `StripeAuth`: the key, `Stripe-Version`, `Stripe-Account`, idempotency keys, retry rules, the files host | **yes** |
| `src/stripe_apiroute/__init__.py` | Package docstring | yes |
| `src/stripe_apiroute/spec_info.py` | The spec's API version and per-operation hosts, written by `generate.py` | never |
| `src/stripe_apiroute/api/` | The generated client (every file starts with `# Generated by apiroute`) | **never** |
| `tests/` | Config checks, auth, the name map; `tests/live/` against Stripe's test mode | yes |
| `.github/workflows/` | `ci.yml`, `build.yml` (regenerate, live-test and commit), `release.yml` (every push to main: tag, PyPI, GitHub release) | yes |
| `.agent/skills/apiroute-client.md` | Skill for creating and maintaining repos like this one | yes |

## Rules

- **Never edit generated code.** CI regenerates from `specs/` and fails on any difference. To change generated output:
  - Edit `apis.yaml`, `auth.py` or `scripts/stripe_names.py` and regenerate.
  - If the generator itself is wrong, fix apiroute; the Build workflow picks up its next release.
- **Regenerate after any change** to `apis.yaml` or the scripts: `uv run python scripts/generate.py`. Add `--fetch` to download the latest spec first. Commit the specs and the generated code together.
- **Live tests use test mode only.** They read `STRIPE_TEST_SECRET_KEY` and refuse any key that isn't `sk_test_…` or `rk_test_…`. Never print a key or write one to a file. Clean up what a test creates.
- **Every merge to main is a release.** There's no release PR; `release.yml` tests, tags and publishes each push to main, Build's commits included.
- **Use conventional commits.** The version comes from the commits since the last tag:
  - `feat!:` (or a `BREAKING CHANGE:` footer) is a major release
  - `feat:` is a minor release
  - anything else (`fix:`, `docs:`, `chore:` ...) is a patch
- **The version lives in the git tag**, not `pyproject.toml` (hatch-vcs). Never tag by hand; the release workflow does.
- **Don't edit CHANGELOG.md by hand;** the release commits write it.
- **Before committing:** `uv run ruff check .`, `uv run ruff format --check .` and `uv run pytest`. After regenerating, also run the live tests: `STRIPE_TEST_SECRET_KEY=sk_test_... uv run pytest tests/live`.

## Common tasks

- **Generation fails with "--operation-names: … both X and Y":** Stripe added an operation whose name clashes with another in the same section. Adjust the rules in `scripts/stripe_names.py` (and its tests), then regenerate. `tests/test_apis_config.py` also fails when an operation has no name.
- **A spec change broke generation:** the Build workflow fails before committing anything. Reproduce with `scripts/generate.py --fetch`, then fix apiroute, `stripe_names.py` or `auth.py`. Patching `specs/` by hand would be overwritten by the next fetch.
- **A live test fails after a spec update:** the spec and Stripe's responses disagree, or a typed model is wrong. Check the failing response; fix apiroute if the generator is at fault, or set `nullable_fields: true` in `apis.yaml` if the spec says a field is never null when Stripe sends null.
- **Release:** nothing to do. Every push to main, and every Build commit, is tested, released and published.
